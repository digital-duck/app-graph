# app-graph apps — migration plan and index

> **Note (app-graph 0.2.0):** this page was carried over from graph-code. The build history below was recorded with graph-code's `spl3` pipeline (so names like `spl/tools.py` and `integrate_system.spl` in the narrative are the old ones); the commands are updated to the current CLI. To build today, run `appgraph build apps/<app>/blueprint/main.graph.yaml`, which uses the GraphLang recipes (see `docs/GUIDE/User-Guide.md`). The per-node cache folder is now `.agr_cache/` (graph-code's `.spl_cache/` has the same layout: rename it to reuse it).


Tracks every app under this directory: its status, its blueprint's shape, and — for apps
migrated from `graph-driven-workflow/apps/SPL/` — what's left to do. Every `.graph.yaml` file
lives under `apps/<app>/blueprint/` (mandatory convention since 2026-08-13, see
`docs/DEV/BUILD/blueprint-schema-v2.2.md`'s "blueprint/ subfolder convention" addendum) —
generated code sits at `apps/<app>/<component>/`, a sibling of `blueprint/`, never inside it.

**Balanced coverage note**: every reference app above is `integrated` at the system level —
that's inherent to the `main.graph.yaml` + component(s) shape all 8 source apps share (CRUD web
apps, request/response, no event bus, no curriculum structure). Domain-type diversity in this
repo currently lives entirely in the fixtures table below (`curriculum`, `reactive_app`,
`workflow`, and bare `software` components) — none of it in a full buildable app yet. If
"balanced coverage across domain types" means a real *app* exercising `reactive_app` or
`workflow` end-to-end (not just a fixture), that's a gap none of the 8 ported apps will close,
since all 8 sources are conventional CRUD apps — worth flagging as a candidate for a 9th,
purpose-built app rather than expecting it to fall out of this migration list.

**Migration process** (established across `todo`→`dispatch`→`expense`): read the source
`system.yaml` + component `graph.yaml`(s) in `graph-driven-workflow/apps/SPL/<app>/`, author
`apps/<app>/blueprint/{main,backend[,frontend]}.graph.yaml` in the current schema (`form.nodes`
with `kind`/`defines`/`composed_of`/`tier`/`spec.interface`/`spec.contract`, `blueprint:`
provenance block, `tech_profile`/`port` orchestration fields), validate with zero LLM cost
(`appgraph.load_domain()` + `validate_full()`), seed pre-authored test fixtures
(`tests/`, and for `vue_typescript` frontends also `package.json`/etc + `npm install`) into the
default output location, then run 

```bash
appgraph build apps/<app>/blueprint/main.graph.yaml --llm claude_cli
``` 
for real and iterate on whatever the run surfaces — every app so far has needed at least one real bug found-and-fixed
this way, never zero.

## Pattern-reference fixtures

`.graph.yaml` files directly under `apps/`). Originally **not** buildable apps in the `todo`/
`dispatch`/`expense` sense — most had no `spec.interface`/`spec.contract` detailed enough for
code generation, no `requirements`/`readme` doc nodes, sometimes just 1-2 nodes; they existed
purely to exercise specific `graph_code` library behaviors and are directly referenced by
`tests/test_graph_lib.py`. As of 2026-08-13 most of the table below has since been migrated to a
