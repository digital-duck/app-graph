app-graph

Build application from graph.yaml blueprint.


wen.gong.research@gmail.com

https://github.com/digital-duck/app-graph
app-graph is an app builder. You describe an app, or a curriculum, as a graph blueprint. app-graph validates it and generates tested code from it with an LLM.

    The problem: code and design drift apart

    • We built a real todo app as two parts, a backend and a frontend, from their blueprints.
    • The frontend's toggleTodo came out as PATCH. The backend and the frontend's own declared contract both said PUT.
    • The VITE_API_BASE_URL setting was missing, so the frontend quietly fetched undefined/todos.
    • Each component's own tests passed. Neither bug was caught until the two ran together.

    Two integration bugs

    ✔ backend tests passed
    ✔ frontend tests passed
    The system was still broken
    This happened in a real build of the todo app. Both bugs only showed up when the two components ran as one system. This kind of drift between the code and the declared design is what the project is built to catch.

    The idea: the graph comes first

    • A blueprint is a graph of typed nodes and edges in the Unified Duality Graph Schema v2.1+.
    • The implementation is generated from the graph. The graph is not a diagram drawn from existing code.
    • It is based on the form/function duality. Form is structure and composition, and it never cycles.
    • Function is behaviour and interaction, and it may cycle (feedback, recursion).
    • One schema serves several targets: curriculum prose as well as software.
    The design rests on one principle taken from natural science: every system has a form and a function. Form relationships are acyclic, so a DAG models them. Function relationships may contain cycles.

    Two graphs in one GraphDomain

    GraphHoldsDirectionMay cycle?
    form_graphPrimitives and form.nodes: the what (components, docs, steps)dep → nodeNo, always a DAG
    event_graphBipartite graph of nodes and events: the reactive behaviournode → event, event → nodeYes

    Every parsed graph becomes a GraphDomain, built by load_domain() in src/appgraph/loader.py.

    The loader turns each YAML file into one GraphDomain that holds two graphs. The form graph sets the build order, so it must be acyclic. The event graph describes reactive behaviour and is allowed to have cycles.

    What a node carries

    Read by a build

    spec.interface
    spec.contract
    verification

    Edges

    Mandatory: composed_of, depends_on
    Optional: enriched_by, optionally_depends_on
    App level: needs
    A build uses the interface, the contract and the verification fields to generate each node and test it. Optional edges have their own fields instead of a boolean flag. The needs field states a dependency at the application level.

    Checks before any model call

    • validate_full() runs the acyclic check, the Two-Radical check, events, call contracts and transitions.
    • On a hard failure it raises ToolFailed, before any LLM call.
    • Warnings that are not fatal come back as ValidationWarning.
    • Example: mealie's 11 frontend↔backend call contracts were confirmed correct before any code was generated.
    # the system and every import
appgraph validate \
  apps/todo/blueprint/main.graph.yaml
    Validation is pure Python and makes no model call. It has caught real authoring mistakes at no cost. Stopping with an error before generation is cheaper than finding the problem after it.

    From graph-code to app-graph

    graph-code (grafcode 0.1.1)

    LLM workflows were .spl scripts
    run by spl3
    left unchanged

    app-graph

    LLM workflows are GraphLang recipes
    you can validate, draw, cap, checkpoint and log them
    model calls go through dd-llm, tests run in Docker

    The blueprint schema, the graph library and the CLI did not change. The migration is recorded in docs/DEV/graflang-refactor.md.

    app-graph continues graph-code, and only the engine changed. Each recipe is now itself a graph, so the same tooling applies to it. graph-code stays as it was.

    Three recipes

    RecipeUsed byWhat it does
    build_componentbuild on a componentFor each node in build order: write, cache, check the node and its edges, refine once if needed. Then test, and repair the failing node up to --max-test-attempts times.
    build_appbuild on a graph with imports:Runs build_component per component, then writes and runs acceptance tests against the live backend and writes the README. Stops at the first failure.
    compile_blueprintextract --llmClassifies the repo's shape, drafts one blueprint or three, then validates, repairs and writes each one.
    All three recipes are in src/appgraph/recipes. The deterministic steps, such as reading, caching, writing, verifying and testing, are plain Python functions in appgraph.build. A recipe calls them as a tool step.

    Rules every recipe follows

    • Each prompt is a file under the recipe's prompts/ folder.
    • Every step that writes files first passes a Cedar policy (policies/*.cedar). Writes are allowed only under your home folder or the temporary folder.
    • Every run has a cap on model calls and writes a log under ~/app-graph/logs/.
    • Code is cached per node in <output>/.spl_cache/. Both graph-code and app-graph can read this cache.
    • extract --llm keeps a checkpoint, so a pass that died partway resumes where it stopped.
    These rules apply to every recipe, not just one. The call cap and the logs keep spending visible. The cache means unchanged nodes are not generated again.

    Tests in containers with no network

    Python components

    image appgraph-verify:py3.12
    built once, by hand

    Vue components

    image appgraph-verify-node:<hash>, from node:22
    made from the component's package-lock.json
    built automatically the first time

    Nothing is mounted from your disk. The code goes in on stdin, and the containers have no network access.

    Generated code is never run directly on your machine. A Vue component needs a lockfile, so run npm install once in its folder. Because nothing is mounted, the container cannot touch your files.

    Blueprints record where they came from (v2.2)

    blueprint:
  id: todo_app_backend
  schema_version: "2.2"
  domain_type: software
  provenance: authored
  parent_blueprint: null
  lineage:
    - pass: forward
      model: claude-sonnet-4-6
      adapter: claude_cli
      prompt_hash: "sha256:ab34…"
      timestamp: "2026-08-11T14:02:11Z"
    • provenance is one of authored, build, reverse or roundtrip.
    • parent_blueprint names the blueprint this one was derived from.
    • lineage: is append-only, with one entry per pass.
    • Every field is optional. A v2.1 graph parses as before.
    Schema v2.2 adds a block that makes the blueprint an object with a history. The lineage log ties any drift to a specific model and configuration. The addition is purely additive.

    Drift between two blueprints

    • appgraph drift <graph_a> <graph_b> reports five components in this order: intent, behavior, structural, interface, implementation.
    • structural, interface, behavior and implementation are graph diffs matched by node id.
    • intent is judged by the model given with --llm, in one dd-llm call. Without --llm it is absent.
    • --dims limits which components run.
    • The report is only printed. Nothing is written back to either blueprint.

    Order, top-down

    intent: why
    behavior: what it should do
    structural: how it is shaped
    interface: how it is exposed
    implementation: how it is built
    The order goes from the most abstract component down to the concrete one: concept before mechanism. Four components are free graph diffs. Only intent needs a model.

    Example: the todo app

    $ appgraph order \
    apps/todo/blueprint/backend.graph.yaml
0 db_connection
1 requirements
2 data_schema
3 orm_model
...
    • An earlier real build (graph-code, claude_cli) passed 22/22 backend tests and 14/14 frontend tests.
    • In the recipe tests, the todo backend comes out byte for byte the same in 7 model calls.
    • When the cache has it, it takes 0 calls.
    The build order comes straight from the form graph. The 22 and 14 test results come from the first real round-trip build. The byte-for-byte check compares the new recipes with graph-code's output, using a scripted model.

    Demo

    # 1. check the system and every import
appgraph validate apps/todo/blueprint/main.graph.yaml

# 2. build one component, capped at 12 model calls
appgraph build apps/jwt_provider/blueprint/component.graph.yaml \
  --max-llm-calls 12

# 3. browse every app's graph
appgraph ide --apps-root apps
    Demo Run validate, start the capped build and watch its log, then open the Graph IDE.
    Validate makes no model call. Build calls the model through claude_cli by default and needs Docker. The IDE starts a backend on port 8880 and a frontend on port 8881.

    Reverse pass: repo to blueprint

    • appgraph extract scans an existing repo with AST and regex rules: FastAPI routes, Pydantic schemas, SQLAlchemy models, Vue components and more.
    • It writes draft blueprints with TODO: markers, by default to ~/app-graph/output/<app-name>.
    • --llm adds the compile_blueprint recipe. Its output is tagged provenance: reverse.
    • --max-llm-calls caps the pass (default 20), and --skip-cache starts it again from scratch.
    • fief is a real example: apps/fief/EXTRACTION.md.
    The forward pass turns a blueprint into code, and the reverse pass turns code into a blueprint. Each draft is validated and repaired up to two times by default. If no tech profile fits, the pass also writes a draft profile for you to review.

    How to try it

    pip install app-graph        # Python 3.11 or later

# once, from a checkout: the Python test image
docker build -t appgraph-verify:py3.12 \
  -f src/appgraph/docker/python.Dockerfile \
  src/appgraph/docker
    • Choose a model with --llm ADAPTER[:MODEL]. The default is claude_cli.
    • Output goes under ~/app-graph/: input, output, report, ide and logs.
    • Override with --output-dir, --input-dir, --out or --apps-root.
    From a checkout, use pip install -e with the dev extras instead. The full command reference is in the User Guide. These folders are created the first time they are used.

    Running the project's tests

    pytest                    # about 2 minutes with Docker
pytest -k "contract" -v   # by keyword
    • The recipe tests use a scripted model, so they make no real LLM calls.
    • The build tests need Docker and the appgraph-verify:py3.12 image. They are skipped when Docker is absent.
    • The recipes are checked against graph-code's own output.
    The suite costs nothing in model calls. Pytest is already configured in pyproject.toml. Without Docker the suite still runs, but the build tests are skipped.

    What is not done yet

    • Drift is never written back to a blueprint's drift: block. The report is only printed.
    • parent_blueprint is not enforced by the parser, even when provenance is reverse or roundtrip.
    • The project is marked Alpha (version 0.2.0).
    • The IDE's Vue frontend needs a manual, one-time npm install.
    • The reverse pass has one real example so far: fief.
    The forward pass works for components and for integrated apps. The round-trip measurement is only partly in place. A future validate_full check could enforce parent_blueprint, but that check does not exist yet.
